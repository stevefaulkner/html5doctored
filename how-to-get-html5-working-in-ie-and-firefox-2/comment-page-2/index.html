How to get HTML5 working in IE and Firefox 2

HTML5 may be the latest and greatest technology, but some browsers don’t have native support for the new semantic elements. Let’s forget for a minute about the even sexier functionality that the elements can bring, such as full control over the <video> element, and just focus on getting the elements to be rendered.

The problematic a-grade browsers are: IE8 and below, and Firefox 2 and Camino 1 (these two browsers use the same rendering engine, which is why they’re both affected).

IE doesn’t style HTML5 elements

IE has it’s own set of issues compared to the Firefox issues which I’ll discuss next. IE quite simply doesn’t see the elements for them to be styled.

This means if you have an <aside> that floats to the right, IE isn’t going to style the element what so ever, because it just doesn’t acknowledge it’s existence.

In fact, this is exactly the same issue that we had before HTML5, where the <abbr> element couldn’t be styled in IE6 – so all manner of work arounds were created (let me add that we’ll also fix the <abbr> element while we fix IE to recognise HTML5).

The fix

There is hope! We can use JavaScript to trigger those elements under IE’s nose so that you’re able to style. This fix works in IE6 and above (the a-grade browsers).

This is achieved by using an HTML5 shiv posted by Sjoerd Visscher.

The fix is to simply create the new element using JavaScript, and voilà, IE is able to style the elements:

document.createElement('header');

For example, say you wanted to style the <time> element to italics, here’s the problem we see:

<!DOCTYPE html>
<html>
<head>
  <title>Header test</title>
  <style>
  time { font-style: italic; }
  </style>
</head>
<body>
  <time datetime="2009-09-13">my birthday</time>
</body>
</html>

In IE before we apply the fix:

And now by including the fix:

<!DOCTYPE html>
<html>
<head>
  <title>Header test</title>
  <style>
  time { font-style: italic; }
  </style>
  <script>document.createElement('time');</script>
</head>
<body>
  <time datetime="2009-09-13">my birthday</time>
</body>
</html>

And now after we have the fix – it’s correctly styled:

One hit solution

For convenience, I wrote a single JavaScript file that can be included to trigger all the HTML5 elements (and the <abbr> element) in to existence for IE.

Download the IE HTML5 enabling script

Include the script in your <head> tag and it will allow you to style the elements appropriately in IE:

<!--[if lte IE 8]>
<script src="html5.js" type="text/javascript"></script>
<![endif]-->

Note that I’ve used a conditional comment to only apply this to IE8 and below. It’s my hope that IE9 and onwards will support HTML5 elements – but when that day comes, make sure to double check the conditional!

Conditions & Gotchas

JavaScript required

Of course this means that you design now depends on JavaScript. My personal feeling on this, is if you’ve used semantic markup for your site, then when the elements can’t be styled, the content is still completely readable.

Here’s a screenshot of the Full Frontal web site, written using HTML5 elements, with and without JavaScript enabled in IE – you can see the content is still readable because it cascades down correctly (similarly as if CSS was disabled):

A little head is always good

If you create the new element, and don’t use a <body> tag (which is perfectly valid), IE will put all those created elements inside the <head> tag. Pretty crazy, but something that’s easily avoided if you always use the <head> and <body> tags in your markup. Leif Halvard explains further with demos

Firefox 2 and Camino rendering bug

Both Firefox 2 and Camino run have a bug in the render engine, specifically the versions prior to 1.9b5:

Firefox 2 (or any other Gecko-based browser with a Gecko version pre 1.9b5) has a parsing bug where it will close an unknown element when it sees the start tag of a “block” element like p, h1, div, and so forth.

According to the W3 Schools stats, Firefox 2 only has around 3% of the market – which may be low enough to justify ignoring.

However, without addressing this issue, a site can look really quite bad in these rendering engines.

The bug is to do with how the Gecko rendering engine doesn’t recognise the new elements. Roughly explained: when Gecko runs in to an unknown element, in removes it’s contents, and puts it next to the element.

For example, the following code:

<body>
  <header><h1>Title</h1></header>
  <article><p>...</p></article>
</body>

Is rendered as if the markup were:

<body>
  <header></header>
  <h1>Title</h1>
  <article></article>
  <p>...</p>
</body>

The visual result is similar to IE running without JavaScript – though subtly different, as the DOM tree is actually in a different order to how you intended as an author.

The fix

There’s two approaches to fixing this issue, and so far I’ve only successfully been able to use the non-JavaScript approach.

The JavaScript approach is to cycle through the DOM tree rearranging the elements as the issues are encountered.

Simon Pieters has a small working example of how this can be done (towards the bottom of the page), however in practise I personally found it didn’t work for my markup. It’s definitely solvable using JavaScript, but it still needs work to have something that works for all permutations of markup.

The second approach is to serve Gecko XHTML. I’ve found this to be the easier approach if you’re either generating a page dynamically using something like PHP, or if you can create your own .htaccess file to make use of mod_rewrite.

XHTML

The first change in the markup you need to include is the <html> tag needs the xmlns attribute – so add this to all your pages:

<html lang="en" xmlns="http://www.w3.org/1999/xhtml">

Next we need to sniff the user agent string (typically a bad approach, but justifiable for our 3% of Firefox users). If the Gecko build is less than 1.9 then we need to serve the content type as application/xhtml+xml.

If you want to use mod_rewrite in an .htaccess file (or the httpd.conf file), you need the following rules:

RewriteCond %{REQUEST_URI} \.html$
RewriteCond %{HTTP_USER_AGENT} rv:1\.(([1-8]|9pre|9a|9b[0-4])\.[0-9.]+).*Gecko
RewriteRule .* - [T=application/xhtml+xml]

This rule sends the xhtml content-type to all Gecko based browsers where version is less than 1.9, or “rv:1.9pre” or “rv:1.9a” or “rv:1.9bx” where x is less than 5.

If you don’t want to use the mod_rewrite approach, you’ll need to manually send the header in your server side scripts.

Here’s the solution for a PHP script:

if (preg_match('/rv:1\.(([1-8]|9pre|9a|9b[0-4])\.[0-9.]+).*Gecko/', $_SERVER['HTTP_USER_AGENT'])) {
    header('Content-type: application/xhtml+xml');
}

This snippet needs to be the first thing that’s printed by your script – i.e. as early as possible in your code.

Gotcha: Yellow Screen of Death

The Yellow Screen of Death is where there’s an XML error on the page. If we’re serving markup as XML and telling the browser to strictly interpret this as XML, if we serve any characters it doesn’t know about, it’s going to bork:

There’s a few places where this can be a problem.

Strict markup

You need to ensure your markup is squeaky clean, but that’s easy, because you’re already a markup Jedi, right?

HTML entities

HTML entities are a no-no. i.e. &bull; isn’t going to fly. You need to use XML entities – which are the numerical representation of these characters.

I built a tool a while back that shows you the HTML entity and the XML value of that entity so you can look them up: HTML entity lookup.

For example: &bull; is 8226, so the XML entity is &#8226;.

User generated content

If your site relies on any user generated content, for example: blog comments, then you need to sanitise the output to ensure there’s no validation issues to trigger the Yellow Screen of Death.

This last issue alone may be justification to investigate the JavaScript solution further.

That all said and done, Firefox has a very good automated upgrade path, and looking at the stats on W3Schools, I think it’s safe to say the market share with this Gecko bug is going to deplete very quickly to nothing.
